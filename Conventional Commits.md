# **Соглашение о коммитах (Conventional Commits)**

Этот документ описывает правила оформления коммитов в проекте. Цель — единообразная и читаемая история изменений, из которой легко понять, что и зачем менялось.

---

## **1\. Формат коммита**

\<тип\>(\<область\>): \<краткое описание\>

\<тело коммита — опционально\>

\<футер — опционально\>

**Пример:**

feat(auth): добавить авторизацию через Google

Реализована OAuth2-авторизация через Google Sign-In.  
Добавлена кнопка входа на странице логина, обработка  
токена и создание сессии пользователя.

Closes \#42

---

## **2\. Типы коммитов**

| Тип | Когда использовать |
| ----- | ----- |
| `feat` | Новая функциональность |
| `fix` | Исправление бага |
| `docs` | Изменения только в документации |
| `style` | Форматирование, отступы, точки с запятой — без изменения логики |
| `refactor` | Изменение кода без исправления бага и без новой функциональности |
| `perf` | Изменения, улучшающие производительность |
| `test` | Добавление или исправление тестов |
| `chore` | Рутинные задачи: зависимости, конфиги, сборка |
| `ci` | Изменения в CI/CD (GitHub Actions и т.п.) |
| `revert` | Откат предыдущего коммита |

---

## **3\. Область (scope)**

Область — необязательная часть в скобках, указывающая, какой модуль/часть приложения затронута.

**Примеры областей для веб\-приложения:**

feat(auth): ...  
fix(cart): ...  
feat(api): ...  
style(header): ...  
refactor(db): ...

Если изменение затрагивает весь проект или не привязано к конкретному модулю — область можно опустить:

chore: обновить зависимости

> Договоритесь между собой о списке типовых областей для вашего проекта (например: `auth`, `api`, `ui`, `db`, `cart`, `payments`) и добавьте их сюда по мере роста проекта.

---

## **4\. Описание (subject)**

* Пишем в повелительном наклонении: «добавить», «исправить», «убрать» (а не «добавил», «добавляет»)  
* Первая буква — строчная  
* Без точки в конце  
* Длина — до **72 символов**  
* Кратко и по существу — что сделано, а не как

**Хорошо:**

fix(cart): исправить пересчёт суммы при удалении товара

**Плохо:**

Fix bug.  
поправил немного корзину, там было не так

---

## **5\. Тело коммита (body) — опционально**

Используется, если краткого описания недостаточно, чтобы объяснить **что** и **почему** было изменено.

* Отделяется от заголовка пустой строкой  
* Пишем обычным текстом, можно списком  
* Объясняем причину изменения, а не пересказываем код

fix(payments): исправить округление суммы заказа

Ранее сумма округлялась в меньшую сторону из\-за  
использования Math.floor вместо toFixed, что приводило  
к расхождению с суммой на стороне платёжного шлюза.

---

## **6\. Футер (footer) — опционально**

Используется для:

Ссылки на задачи/issue:  
 Closes \#42Refs \#17

* 

Breaking changes (несовместимые изменения):  
 BREAKING CHANGE: изменена структура ответа API /users,поле \`name\` заменено на \`firstName\` и \`lastName\`

* 

---

## **7\. Breaking changes**

Если коммит ломает обратную совместимость — обязательно укажите это одним из способов:

**футер `BREAKING CHANGE:`**

feat(api): изменить формат ответа эндпоинта /users

BREAKING CHANGE: поле name заменено на firstName и lastName

---

## **8\. Примеры "до/после"**

**До:**

поправил баг  
работа над авторизацией  
wip  
fix

**После:**

fix(cart): исправить пересчёт суммы при удалении товара  
feat(auth): добавить валидацию email при регистрации  
refactor(api): вынести обработку ошибок в отдельный middleware  
chore: обновить зависимости до последних минорных версий

---

## **9\. Правила для нас двоих**

* \[ \] Один коммит — одно логическое изменение (не смешиваем `feat` и `fix` в одном коммите)  
* \[ \] Пишем описание на **русском / английском** *(зачеркнуть лишнее — договоритесь)*  
* \[ \] Если коммит закрывает задачу — указываем `Closes #<номер>`  
* \[ \] Перед пушем в общую ветку проверяем, что коммиты не содержат `wip`, `test123`, `asdasd` и т.п. — при необходимости делаем `rebase -i` и приводим историю в порядок  
* \[ \] Breaking changes всегда помечаем явно

---

## **10\. Полезно (по желанию, на будущее)**

Когда проект подрастёт, можно подключить:

* **commitlint** — автоматическая проверка формата коммитов перед пушем/коммитом (через husky)  
* **semantic-release** — автоматическая генерация версии и CHANGELOG.md на основе типов коммитов (`feat` → minor, `fix` → patch, `BREAKING CHANGE` → major)

Пока эти инструменты не обязательны — можно первое время следить за форматом вручную и подключить автоматизацию позже, когда почувствуете в этом необходимость.
